# 立项资料编写方法论（内容红线与自检）

> 本文件回答"内容怎么写才算合格"。版式不属本技能范围；历史版式规格已归档至 `archive/references/zone-spec.md`。

## 领导的本质：资源分配官

立项评审的五个核心问题，也是立项内容的叙事顺序：

| 问题 | 对应栏目 |
|---|---|
| 项目为什么做（来源与价值） | 标签牌 + 需求背景 + 应用场景及客户痛点 |
| 做什么样（产品定义） | 产品定义 |
| 谁来做（各部门职责） | 承接单位 + 项目团队 |
| 做多久（关键节点） | 项目计划 P1-P4 |
| 有什么风险（预案） | 风险预案 + 有条件立项条件 |

## 六条内容红线

### 1. 数字化：减少形容词，用具体数值
- ✗ "老产品产出良好" → ✓ "销售额 2000 万，超原预测 237%，投入产出比 980%"
- ✗ "环境适应性好" → ✓ "70℃ 降容 ≤10%（现有 15%）"
- 痛点、改善、成本、周期——每一处都要有数字或百分比对比。

### 2. 痛点与产品定义一一对应
左列痛点 1、2、3 → 「产品定义 · 性能及质量可靠性」逐条回应（尺寸给 mm、时间给 ms、成本给 %），不能堆砌无关参数。
例："体积过大"→"外形尺寸 XX mm"；"动作时间过长"→"分段时间 XX ms"。

### 3. 销售预测必须交叉验证
独立推算链路：行业总出货量 → 单台/单kW用量 → 总需求量 → 中标份额 → 与客户/销售给的预测对比。
- 偏差在合理范围内 → 证明预测可靠；
- 所有市场数据标注来源（行业协会、标准、盘厂调研）；
- 份额按历史保守取值（如老产品 60% → 预测用 40%）。
- 呈现保守/乐观双口径，展示风险可控。

### 4. 有风险必须附预案
风险不能只列出来。每条风险四要素：**风险 / 影响 / 应对预案（含具体降本或补救措施与量化幅度）/ 资源诉求（+责任人）**。
让老板做判断，而不是替老板出主意。

### 5. 技术可行性如实标注
- 成本、周期、性能全部满足 → `可行`
- 存在不满足项 → `部分可行` + 红色"暂不满足"行 + 风险预案
- ✗ 明知不满足还写"可行"。
- 同理生产可行性（人员/设备/场地/物料逐一核对）。

### 6. 命名与口径规范
- 产品平台只允许：**昆仑、新锐、诺雅克**；禁止"5 系列""9 系列"等非标准表述。
- 财务数据由财务提供（非产品经理自行测算）；技术方案由研发提供；成本由采购提供；产品经理负责整体框架与拉通。
- 三层价值判断（单一客户定制项目适用）：直接效益 / 技术积累 / 战略卡位——短期毛利不达标不等于不立项，写清让领导做战略判断。

## 领导常问六问（交付前自检清单）

生成后逐问自答，答不上来的回改 spec：

1. 项目靠不靠谱？——历史合作数据证明客户可信度（需求背景有无来源佐证）。
2. 预测数据站不站得住脚？——数据来源标注 + 销售预测交叉验证。
3. 产品核心价值点（USP）是什么？——解决痛点 / 满足标准 / 价格优势 / 整套方案，至少一个说清。
4. 市场定位和定价逻辑？——比竞品贵/便宜的理由。
5. 销售预测能否达成？——交叉验证 + 保守口径 + 客户清单支撑。
6. 系统解决方案完整吗？——本产品进入场景后，配套产品（现有/规划/开发中）能否跟上；必要时在需求背景补充典型配置方案。

## 常见退回原因（rationalization 表）

| 借口 | 现实 |
|---|---|
| "数据还没有，先定性描述" | 无数字的痛点/收益在评审会被直接退回；宁可标注"待财务确认"也给出口径 |
| "风险写了领导会觉得项目不行" | 不写风险而上会，领导发现后才是信任问题；预案齐全反而体现掌控力 |
| "交叉验证太费事，销售拍胸脯了" | 销售预测未经独立推算 = 立项最大被质疑点；历史教训"承诺几百万，上市零产出" |
| "可行性先写可行，细节后面补" | 领导对"部分可行 + 预案"的信任度远高于被戳穿的"可行" |
| "平台写 5 系列大家看得懂" | 非标准平台名在评审系统与规划池中无法归口，直接退回 |
